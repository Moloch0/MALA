# 为什么解释状态难以控制流化

## 1. 问题

当一个任务开始失控时，人很自然会想：

- 能不能把它拆成状态
- 能不能把状态写成字段
- 能不能让系统而不是对话来维护这些状态

这个想法在很多工程任务里是成立的。  
如果状态是硬的、离散的、低语义的，那么控制流化往往有效。

但在“问题构造”“澄清目标”“辨认真正未知项”“判断冲突是否阻断回答”这类任务里，事情不同。

这里真正困难的状态，不是对象状态，而是解释状态。

因此，问题不是“状态能不能存起来”，而是：

**解释状态能不能被低成本地重新理解。**

如果不能，那么控制流化就会遇到一个根本障碍：

你虽然把状态存下来了，但并没有把理解负担卸下来。

## 2. 什么是解释状态

解释状态，不是指“有一段解释”，而是指：

**某个任务当前之所以能继续推进，依赖于一组必须被重新理解的语义关系。**

例如在问题构造里，下面这些都属于解释状态：

- 这个目标为什么是真目标，而不是顺手拿来的代理目标
- 这句话为什么构成未知项，而不是只是态度表达
- 这两个说法到底是互补、并列，还是冲突
- 这轮澄清到底缩小了问题，还是只是改写了措辞
- 用户否定的到底是答案内容，还是你对问题的建模方式

这些状态都不是简单的布尔值、枚举值或计数器。  
它们依赖上下文、依赖用词、依赖语气、依赖之前被修正过的路径。

所以解释状态的关键特征是：

- 它不是纯字段
- 它不能脱离上下文独立成立
- 它必须被重新解释，而不是只被重新读取

## 3. 为什么解释状态难以结构化

解释状态不是完全不能结构化，而是很难以低损耗方式结构化。

### 3.1 字段能保存结论，不能保存结论成立的语义张力

你当然可以写：

- `target = "比较 A 与 B"`
- `issue = "mixed"`
- `blocked_by = ["criterion missing"]`

但这类字段只能保存某种压缩后的结论。  
它们往往保存不了结论之所以成立的语义张力，例如：

- 为什么这里算 `mixed`，而不是 `missing`
- 为什么这个 `target` 是用户真正想比较的，而不是中途借来的表达
- 为什么这个缺失会阻断回答，而另一个缺失不会

一旦这些关系丢了，agent 下轮面对这些字段时，仍然要重新猜它们到底意味着什么。

### 3.2 一旦为保真而补充说明，状态又重新膨胀成文本

如果你意识到字段太薄，就会自然补更多解释：

- `basis`
- `note`
- `conflict_reason`
- `why_blocking`
- `why_not_other_diagnosis`

但一旦补到这个程度，状态就开始重新变成长文本。  
而长文本一旦回来，就不再是“硬状态”，而是“等待再次解释的文本状态”。

这时你只是把原来的对话，换了一种更别扭的形式重新存了一遍。

### 3.3 解释状态的边界经常会漂移

在问题构造这类任务里，很多状态不是静态对象，而是随着理解推进不断重定义的。

例如：

- 起初看上去是 `missing`
- 后来发现其实是 `mixed`
- 再后来发现不是 `mixed`，而是最初目标就锚错了

这说明解释状态不是“同一对象上的属性逐步填满”，  
而常常是“对象本身的理解框架在变”。

这类变化不是普通字段更新，而是解释框架改写。  
这对控制流系统非常不友好。

## 4. 为什么控制流化没有卸掉复杂度

控制流化真正有价值的前提是：

**复杂度被转移了，而不是被改写了。**

但在解释状态任务中，经常发生的不是转移，而是改写。

### 4.1 从“理解对话”改写成“理解状态表示”

原来 agent 读原始对话。  
现在 agent 不读完整对话，而读：

- 槽位
- issue
- note
- basis
- blocked_by
- history

表面看这是压缩。  
但如果这些东西要足够保真，它们就会携带很强的语义密度。

于是 agent 并没有少做理解工作，  
只是从“理解原对话”改成了“理解一份人为构造的状态表示”。

而后者通常更拧巴，因为它既不如原对话自然，也不如机器状态干净。

### 4.2 从“处理问题”改写成“处理问题与表示之间的映射”

控制流化之后，agent 不再只处理问题本身，还要处理：

- 这个状态字段是否准确
- 当前状态是否遗漏了某个微妙转向
- 字段之间是否仍然保留了原始语义关系
- 当前更新是修问题，还是修表示

因此，新的任务其实变成了：

**一边处理问题，一边处理问题在控制结构中的表示。**

这往往比只处理问题更难。

### 4.3 从“继续对话”改写成“恢复上下文”

对话有一个被低估的优点：

它天然保留了时间顺序、否定痕迹、试探路径和修订历史。

而控制流表示为了压缩，常常会把这些东西抽干。  
于是 agent 每轮都得做一件额外工作：

- 从抽象表示里恢复此前到底发生了什么

也就是说，状态虽然被存下来了，但上下文却没有被便宜地保留下来。  
这正是高 token 的根源之一。

## 5. 为什么“程序维护状态”没有根本改观

程序确实可以维护一些东西：

- 文件是否存在
- 某步是否完成
- 哪个槽位是否已填
- 某条路由是否被走过

这些属于事务状态或部分结构状态。  
在这类场景中，程序维护状态当然有效。

但程序维护不了最困难的那部分：

- 为什么这个值现在仍然可信
- 为什么这个冲突构成阻断
- 为什么这个修订改变了问题身份
- 为什么这次澄清不是偷换，而是真收缩

这些东西一旦写成文本说明，又重新回到需要 agent 再解释的形态。  
于是程序只是保管了状态容器，没有保管真正困难的状态内容。

所以根本问题不是：

- 状态有没有地方存

而是：

- 状态有没有办法在下一轮被低成本、低失真地重新激活

如果不能，控制流化就不会带来根本收益。

## 6. 为什么多 agent 也没有解决问题

把状态交给另一个 agent，看起来像是分工，实际上常常只是转手。

原因很简单：

- 主 agent 需要理解状态
- 子 agent 也需要理解状态
- 两边理解的都是同一份高语义密度材料

如果状态本身不能便宜地解释，那么多 agent 只会带来：

- 更多 token
- 更多同步成本
- 更多状态解释的不一致

换句话说，多 agent 只能切分职责，  
不能替代对解释状态本身的重新理解。

因此，它不构成根本解法。

## 7. 为什么单轮更像最小单元

如果长程解释状态很贵，那么一个自然退路就是：

**不要试图让同一个 agent 长时间在线维护厚重状态，而把单轮视为最小求解单元。**

这样做并没有消灭状态。  
它只是承认：

- 长程一致维护很贵
- 每轮重建局部语境有时更稳
- 让 agent 处理局部高质量判断，可能比让它背长期状态更现实

但这条路也有明显代价：

- token 仍然高
- 对话本身就是重要状态，不能轻易舍弃
- 工程收益未必高于直接长对话

所以单轮化不是胜利，而更像现实妥协。

## 8. 哪些状态适合控制流化，哪些不适合

这件事不能一概而论。  
更准确的区分是：

### 8.1 适合控制流化的状态

- 事务状态
- 资源状态
- 可枚举阶段状态
- 硬约束满足与否
- 机器可验证的写入边界

这些状态的共同点是：

- 可离散化
- 可检查
- 可在下一轮直接读取而不需大规模重新解释

### 8.2 不适合强控制流化的状态

- 目标的真实锚点
- 问题身份是否发生变化
- 冲突是否真正阻断
- 某次澄清是否缩小了语义空间
- 某条修复是否仍忠于用户意图

这些状态的共同点是：

- 高度依赖语境
- 高度依赖解释
- 很难压缩成低损耗表示

因此，它们更适合停留在对话与 skill 层，而不是硬塞进控制流层。

## 9. 回到 `skill-hard`

`skill-hard` 的失败，不是因为它不知道要记录什么。  
它恰恰知道得太多了。

它试图把大量解释状态也一并控制流化，例如：

- 当前主诊断
- 冲突是否编码
- 哪个 failure route 生效
- 某次修订是否意味着版本递增
- 当前是否 ready_for_handoff

这些内容如果放在真正有执行器、审计器和低成本状态回放的系统里，也许有意义。  
但一旦直接放进由 LLM 自己维护的 skill 正文里，就会出问题：

- 解释负担没有消失
- 状态维护负担又额外出现
- 最终模型既要理解问题，又要理解一套关于问题的控制表示

这就是它失败的更深层原因。

## 10. 结论

解释状态难以控制流化，不是因为它无法被存储，  
而是因为它无法被低成本、低失真、低重复地重新理解。

因此，对这类任务来说，真正的瓶颈不是“有没有状态容器”，而是：

**有没有一种中间表示，既足够保真，又足够便宜，能让解释状态在多轮之间被稳定激活。**

在现阶段，这种表示通常还不存在。  
于是最稳妥的现实结论就是：

- 可以对事务状态做控制流化
- 可以对少量结构状态做有限控制流化
- 但不要高估解释状态控制流化的收益

对于“提问作为对话核心”的任务，skill 仍然更接近当前可用的上限。  
控制流不是逻辑上不存在，而是工程上还没有找到足够低损耗的承载方式。
