# 提问作为算法

如果说前面几篇文章只是把问题从语言中剥离出来，那么这一步要更进一步：我们不再把提问看作一种说话行为，而把它看作一种求解结构。

这是一个关键转折。因为一旦这样看，很多原本显得抽象的判断就会突然变得具体。为什么一个好问题会让人“知道下一步该做什么”？为什么一个坏问题会让讨论不断发散，却始终没有进展？为什么有些问题一旦说清楚，方法几乎自己就出来了？这些现象都提示我们：提问并不只是向外索取信息，它实际上在组织一个搜索过程。

一个真正的问题，至少隐含了五样东西：已知条件、未知目标、允许操作、判定标准，以及终止条件。没有已知条件，就无法开始；没有未知目标，就不知道要解什么；没有允许操作，就不知道能做哪些变换；没有判定标准，就不知道什么算解出来；没有终止条件，就不知道何时该停止。只要这五样东西逐渐明确，思考就会开始显露出算法性的骨架。

也正是在这里，提问和普通谈话分道扬镳了。普通谈话可以围绕一个主题不断延展，信息越来越多，结构却未必更清楚。真正的提问则不同。它会迫使你区分什么是相关信息，什么是噪声；什么是当前缺口，什么是后续分支；什么需要被定义，什么需要被验证，什么需要被暂时悬置。于是，思考不再只是“继续说”，而开始表现为一连串明确的操作。

这些操作本身，就是算法性的。

当一个大问题无法直接解决时，我们会把它拆成几个子问题；这就是分解。当一个子问题的求解方式与原问题相似时，我们会重复同样的结构；这就是递归。当一个候选答案必须回到已知条件中检查是否一致时，我们就在做验证。当几种可能性互相冲突时，我们会做排除、反证和消元。当一个问题存在多个展开方向时，我们会比较分支、估计代价、决定先搜哪一条路；这就是搜索与剪枝。

因此，所谓“会思考”，并不只是知道很多内容，更重要的是能不能把模糊的困惑改写成这些操作可以接手的形式。换句话说，提问不是在制造内容，而是在定义一套能持续推进内容的程序。

这里最容易帮助理解的比喻，是搜索树。一个清晰的问题，往往像一棵可以逐步展开的树：当前节点是什么，往下有哪些分支，每个分支需要什么额外信息，哪些分支可以提前剪掉，哪些分支值得继续深入。在这样的结构里，提问并不是盲目地四处发问，而是在决定树如何展开。

但这个比喻也有边界。对于一些成熟的问题，比如算一道题、证明一个引理、做一个诊断，树的节点和分支往往已经很清楚，提问更像是在其中选择路径。而对于真正深的问题，困难甚至还不在“树太大”，而在“树还没有长出来”。这时我们首先要做的，往往不是搜索，而是发明节点是什么、分支规则是什么、哪些变化值得保留、哪些细节应被忽略。也就是说，深问题的第一步不是搜索，而是构造搜索空间。

这时，回答的地位也就更容易看清了。回答通常不像一棵树，而更像某次搜索留下的压缩结果。它可能是一个局部结论、一条经验规则、一个高价值方向，或者一个已经被折叠过的中间结果。它很重要，因为没有这些压缩，搜索就无法积累，也无法传递；但它终究只是搜索过程中的产物，而不是搜索结构本身。

因此，回答更像缓存，提问更像程序。回答保留的是已经得出的东西，提问规定的是接下来如何继续。一个人可以很会缓存，也就是很会复述、总结、组织结论，但如果他不会把新的困惑继续写进可推进的结构里，他的思考能力仍然是有限的。

这一点还有一个更深的含义。既然提问是在组织搜索，那么一个真正好的问题，最终必须满足一个更强的要求：它不仅要能展开，而且要能递归。也就是说，问题推进之后，后续局面仍应当保持某种结构上的可处理性。否则，问题每推进一步，就会把自己变得更不可控，最终重新坠回混沌。

这就把我们带到了下一步。一个能够支持稳定递归求解的问题结构，究竟应该长成什么样子？如果要把这个要求正式写出来，我们很快就会进入一个熟悉而强大的框架：马尔可夫决策过程，也就是 MDP。
