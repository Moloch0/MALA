# MALA-Graph 顶层定位

MALA-Graph 是建立在 MALA-core 之上的问题求解图层。它不直接替代 MALA-core，也不把 MALA-core 改写成另一个回答器；它要做的是把 MALA-core 构造出的“可求解问题”组织成一个可递归展开、可比较分支、可选择下一步动作、并能明确停止的图结构。

如果说 MALA-core 的核心任务是 More Ask, Less Answer，也就是把模糊请求修成可回答、可验证、可推进的问题，那么 MALA-Graph 的核心任务就是把这些被修正过的问题状态放入一个动态结构中，让求解过程不再只是一次 prompt 修复，而是一条可追踪的状态演化路径。

## 一、MALA-Graph 是什么

MALA-Graph 可以被理解为一个问题状态图：

- 节点表示某个已经被结构化的问题状态；
- 边表示一次问题构造、拆分、澄清、验证、剪枝或求解动作；
- 策略决定在当前图上优先展开哪个节点、采取哪类动作、何时停止；
- 终止条件决定什么时候当前图已经足以支持回答、决策或交付。

它关注的不是“给一个输入生成一个最终答案”，而是“把一个尚未成形的任务逐步推进到可求解、可验证、可停止的状态”。因此，MALA-Graph 更接近一个问题构造与求解调度系统，而不是单轮问答模板。

在这个定位下，MALA-Graph 的最小闭环是：

1. 接收一个原始困惑、任务或请求；
2. 用 MALA-core 将其构造成初始问题状态；
3. 把该状态放入 Problem State Graph；
4. 由 SolverPolicy 选择下一步操作；
5. 生成新的问题状态、候选答案或验证结果；
6. 持续展开，直到满足饱满条件或终止条件。

## 二、为什么 MALA-core 是问题构造核心

MALA-Graph 不能绕过 MALA-core，因为图层本身并不自动知道什么是“好节点”。如果节点只是原始话题、愿望、关键词或未经清洗的用户输入，那么图的展开只会把混乱复制到更多分支里。

MALA-core 的作用，是为图层提供问题构造的基本判准。它至少负责把原始输入压成以下结构：

- 已知条件：当前已经可用的信息是什么；
- 未知目标：真正要解的缺口是什么；
- 允许操作：接下来可以做哪些澄清、拆分、查询、推理或验证；
- 判定标准：什么样的结果算有效、充分或更好；
- 终止条件：什么时候可以停止继续提问或继续展开。

这些要素正是 Problem State Graph 的节点语义来源。没有 MALA-core，图上节点很容易只是“文本片段”；有了 MALA-core，节点才可以成为“可递归处理的问题状态”。

因此，MALA-core 是 MALA-Graph 的问题构造核心，原因不是它先存在，也不是它命名上更基础，而是它承担了图结构成立前必须完成的状态抽象工作：把完整、混乱、上下文相关的历史压缩为一个足以支持后续控制的问题状态。

## 三、核心对象一：Problem State Graph

Problem State Graph 是 MALA-Graph 的状态容器。它不是普通知识图谱，也不是概念关系图，而是一个面向求解过程的问题状态图。

一个最小 Problem State 可以包含：

- `problem`: 当前问题表述；
- `knowns`: 已知条件与约束；
- `unknowns`: 尚未解决的关键未知；
- `actions`: 当前可用的推进动作；
- `criteria`: 判断好坏、充分性和正确性的标准；
- `status`: 当前状态，例如 open、expanded、blocked、answerable、resolved；
- `evidence`: 支持该状态的来源、推理或验证记录；
- `parent` / `children`: 该状态在图中的上下游关系；
- `cost` / `value`: 展开成本、预期收益或优先级估计。

图中的边表示从一个问题状态到另一个问题状态的变换。常见边类型包括：

- `clarify`: 澄清概念、对象、范围或约束；
- `decompose`: 把一个问题拆成多个子问题；
- `abstract`: 抽象出更一般的状态表示；
- `specialize`: 收窄到更具体的情形；
- `verify`: 对候选结论进行检验；
- `prune`: 剪掉低价值、重复或不可行动分支；
- `answer`: 从足够饱满的问题状态生成答案；
- `merge`: 合并等价或高度重叠的问题状态。

Problem State Graph 的关键不在“图很大”，而在“图上的状态具有可控语义”。它应当让系统能回答以下问题：

- 当前真正卡住的未知在哪里；
- 哪些分支已经足够回答；
- 哪些分支仍需澄清；
- 哪些分支虽然相关但不值得继续展开；
- 当前是否已经达到可交付状态。

## 四、核心对象二：SolverPolicy

SolverPolicy 是作用在 Problem State Graph 上的求解策略。它不直接等同于答案生成策略，而是决定图如何展开、如何剪枝、如何分配计算预算、何时把问题交给回答过程。

一个 SolverPolicy 至少要处理四类决策：

1. 节点选择：下一步展开哪个 Problem State；
2. 动作选择：对该节点执行澄清、拆分、验证、查询、回答还是剪枝；
3. 预算分配：在深搜、广搜、验证、信息收集和答案生成之间如何分配资源；
4. 停止判断：当前图是否已经饱满，或继续展开是否不再划算。

在形式上，SolverPolicy 可以写成：

```text
policy(graph_state, budget, objective) -> next_action
```

其中 `graph_state` 是当前 Problem State Graph 的整体状态，`budget` 是可用时间、token、工具调用、人工注意力或风险预算，`objective` 是本次任务的目标函数。

SolverPolicy 的质量不只看它能不能最终得到正确答案，还要看它是否避免了两种失败：

- 过早回答：问题状态还没有达到足够结构化，就把局部猜测包装成答案；
- 过度提问：问题已经足以支持行动，却继续展开低收益分支。

因此，SolverPolicy 的核心能力是在“继续构造问题”和“开始给出答案”之间做可解释的切换。

## 五、饱满条件与终止条件

MALA-Graph 需要区分“饱满”和“终止”。

饱满条件描述的是某个问题状态或整张图是否已经具备足够结构，可以支撑下一步回答、决策或交付。它强调的是结构充分性。

一个问题状态可以被称为饱满，通常意味着：

- 关键未知已经被显式列出，而不是隐含在原始话题中；
- 已知条件、边界和约束足以限制答案空间；
- 可用操作和验证路径已经清楚；
- 判定标准足以比较候选答案；
- 继续澄清的边际收益低于当前回答或行动的收益；
- 对高风险分支已有必要的标注、保留或验证计划。

终止条件描述的是当前求解过程是否应当停止。它强调的是过程控制。

常见终止条件包括：

- `answerable`: 图中已有一个或多个节点达到可回答状态；
- `resolved`: 目标问题已经被回答、验证并满足交付标准；
- `budget_exhausted`: 时间、token、工具调用或人工注意力预算耗尽；
- `blocked`: 缺少外部信息、权限、实验条件或用户决策，无法继续推进；
- `low_expected_gain`: 继续展开的预期收益不足以覆盖成本；
- `risk_gate`: 任务风险要求先获得确认、证据或人工介入。

饱满不必然等于终止。一个节点可以已经饱满，因而适合回答；但整张图可能仍有其他分支需要处理。反过来，终止也不必然意味着饱满；预算耗尽、外部阻塞或风险门槛都可能迫使系统停止，并明确报告当前未完成的结构缺口。

## 六、与效率最优主张的关系

MALA-Graph 可以提出效率上的主张，但需要谨慎表达。

较稳妥的说法是：在问题尚未成形、存在隐含未知、约束不清或判定标准缺失的任务中，MALA-Graph 有机会通过显式的问题状态图减少无效回答、重复澄清和错误优化，从而提高单位预算下的求解质量。

更强的说法，例如“MALA-Graph 总是效率最优”或“图化问题构造必然优于直接回答”，目前不应作为无条件结论。原因很简单：

- 对事实查询、简单定义、低风险格式转换等任务，直接回答可能更高效；
- 图构造本身有成本，只有当它减少的错误成本或搜索成本高于自身开销时才划算；
- 最优性必须相对于任务分布、成本模型、风险函数和评价指标来定义；
- 没有基准实验或理论边界时，不能把局部有效经验写成全局最优定理。

因此，MALA-Graph 的效率主张应当限定为条件性命题：

> 在需要先构造问题空间、且错误问题设定会显著放大后续成本的任务中，MALA-Graph 可能比单轮直接回答更有效；其优势应通过任务分布、预算约束、答案质量、纠错成本和人工介入成本共同评估。

如果未来要把这个主张推进为更强的理论命题，就需要补齐至少三件事：

1. 明确定义成本模型，包括 token、时间、工具调用、人工注意力和错误代价；
2. 明确定义收益指标，包括答案正确性、可验证性、可行动性和鲁棒性；
3. 在可复现实验中比较直接回答、MALA-core 单轮修复、MALA-Graph 多步求解三类流程。

## 七、边界

MALA-Graph 的顶层定位应保持清楚边界：

- 它不是替代 MALA-core 的新 core；
- 它不是把所有任务都图化的通用口号；
- 它不是声称任何问题都需要多轮展开；
- 它不是在没有成本模型时宣称效率最优。

它更准确的位置是：

> MALA-core 负责把原始输入构造成可求解问题；MALA-Graph 负责把这些可求解问题组织成可展开、可选择、可验证、可停止的问题状态图；SolverPolicy 则负责在图上进行受预算约束的求解调度。

这个定位保留了 MALA-core 的核心地位，也为后续扩展出更复杂的图搜索、分支管理、验证机制和效率评估留下了空间。
