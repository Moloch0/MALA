# skill 与控制流的分层原则

## 1. 问题不在复杂，而在错层

讨论 skill 与控制流的关系时，最容易犯的错误，是把问题理解成：

- skill 应不应该更简单
- 控制流应不应该更复杂

这两个问题都不是核心。  
真正的核心问题是：

**skill 和控制流属于不同层的东西。**

它们可以描述同一件事，但不是用同一种方式描述，也不是为了同一种目的描述。  
如果把它们写进同一份运行时文本里，问题通常不是“太长”或“太细”，而是：

**发生了层次错位。**

一旦层次错位，模型就会同时被要求做两件彼此牵制的事：

- 作为语义系统去理解任务
- 作为离散系统去维护过程

这才是张力的本质来源。

## 2. skill 是什么

从本质上说，skill 不是流程图，也不是规则表。  
skill 是一种写给 LLM 的高层接口。

它的作用不是把每一步展开，而是给模型一个稳定的语义场，使模型知道：

- 这里到底在做什么
- 什么算做对了
- 什么常见偏差必须避免
- 哪些结构必须被看见

因此，skill 的本质不是“列出所有判断”，而是：

**用尽可能少但足够强的约束，塑造模型的整体判断方向。**

这意味着 skill 依赖的是 LLM 的两种能力：

### 2.1 语义压缩能力

LLM 的强项之一，不是执行显式流程，而是把许多局部迹象压成一个高层判断。  
例如它可以直接看出：

- 这是一个话题，不是问题
- 这是缺项，不是错配
- 这是两个问题混在一起
- 这里如果继续补，就会变成编造

这些判断当然也能事后写成 `if / else`，但模型在运行时并不是靠逐条遍历这些分支来完成的。  
它是在语义空间里整体完成的。

### 2.2 隐式推理能力

一个好的 skill 不需要把全部中间过程显式展开。  
它只要把目标、约束和边界给清楚，模型就能在内部完成大量低层判断。

所以，skill 的工作方式天然偏向：

- 高层
- 稀疏
- 约束性
- 面向整体判断

## 3. 控制流是什么

控制流则完全不同。

控制流的本质，是把一个过程离散化、外显化，并组织成可检查、可追踪、可回滚的结构。

它关心的不是“模型大体上理解了没有”，而是：

- 当前处于哪个状态
- 这个状态允许什么动作
- 某个写入是否合法
- 某个失败应转向哪里
- 什么时候终止
- 什么时候交接

因此，控制流依赖的不是语义压缩，而是：

- 状态显式化
- 分支显式化
- 条件显式化
- 写入边界显式化

换句话说，控制流的工作方式天然偏向：

- 低层
- 稠密
- 可追踪
- 面向过程治理

## 4. 为什么两者必须分离

这不是偏好问题，而是计算形式不同导致的必然要求。

### 4.1 它们服务于不同的计算机制

skill 服务于 LLM 的隐式计算。  
控制流服务于外部系统的显式计算。

前者依赖模型在语义空间中完成压缩、泛化和整体判别。  
后者依赖系统把状态、动作和转移关系写清楚，以便检查和复用。

如果把两者混在一起，就等于要求模型同时用两种彼此牵制的方式工作：

- 一方面要自由压缩
- 一方面又要严格展开

这不是简单的“多做一点工作”，而是要求同一套输出同时满足两套相反的表示要求。

### 4.2 它们需要的表示粒度不同

skill 需要的是粗粒度的不变量。  
例如：

- 目标是什么
- 什么算回答
- 常见失效是什么
- 哪些约束不能破

控制流需要的是细粒度的可区分状态。  
例如：

- 当前诊断是什么
- 是否允许转移
- 是否需要升版本
- 是否允许写某个字段

这两种粒度不能混为一谈。  
因为一旦把细粒度状态塞进 skill，模型就必须把本来可以隐式处理的局部判断，提升为显式上下文负担。

结果是：

- 该由模型内部压缩掉的东西，被迫显式携带
- 该留给任务内容的注意力，被状态维护占据

所以问题不是“细节太多”，而是：

**错误粒度的结构被放进了错误层。**

### 4.3 它们优化的目标不同

skill 的首要目标，是提高任务完成质量。  
它优化的是：

- 问题是否被正确理解
- 输出是否贴近目标
- 模型是否少犯语义性错误

控制流的首要目标，是提高过程治理质量。  
它优化的是：

- 步骤是否可检查
- 状态是否可追踪
- 分支是否可回放
- 交接是否可复现

这两个目标不是同一个目标。  
当它们写在一起时，模型会自然偏向更容易被文本显式检查的那一侧，也就是流程合规，而不是任务完成。

于是目标函数发生偏移：

- 原本应优先解决问题
- 变成优先维持规范长相

这就是很多“复杂 prompt 越写越没用”的深层原因。

### 4.4 它们应对的失败类型不同

skill 主要对抗的是语义漂移。  
例如：

- 把主题当问题
- 把愿望当未知
- 把态度当判准
- 把话说顺了却没补结构

控制流主要对抗的是过程漂移。  
例如：

- 状态混乱
- 来源丢失
- 路由不清
- 写入越界
- 旧结论未经处理继续沿用

这两类失败虽然有关联，但并不相同。  
如果把两者放在一份文本里，模型和人都会逐渐看不清：

- 这条规则到底是在防语义错误
- 还是在防过程错误

一旦看不清，规则就开始自我膨胀。

### 4.5 控制流需要外部可验证性，skill 不需要

这是一个更本质但经常被忽视的点。

控制流之所以有意义，是因为它默认存在一个外部视角，可以检查：

- 你现在的状态标得对不对
- 这个转移是否合法
- 这个字段是不是该写
- 这个失败路由是不是被正确触发

也就是说，控制流天然面向一个外部检查者，或者至少面向一个可反复核对的执行环境。

但单独给 LLM 一份 prompt 时，这种外部可验证性通常并不存在。  
很多状态字段、版本字段、路由字段，并没有真正的执行器去强制它们成立。

于是这些内容会发生退化：

- 从“有效控制”退化为“文本仪式”
- 从“外部约束”退化为“内部表演”

这就是为什么很多看似严格的控制结构，一旦直接塞进 prompt，就会变成低效噪音。

## 5. skill 与控制流的正确关系

两者不是互斥的。  
真正合理的关系不是二选一，而是分工。

### 5.1 skill 提供方向

skill 负责定义：

- 任务是什么
- 何为成功
- 何为典型失败
- 哪些高层约束必须遵守

它不负责把所有低层过程都显式化。

### 5.2 控制流提供治理

控制流负责管理：

- 状态
- 转移
- 路由
- 回滚
- 审计
- 交接

它不负责取代 skill 的语义作用。

### 5.3 二者的连接方式

最稳妥的方式不是把控制流全文写进 skill，  
而是：

- 用 skill 约束模型的高层判断
- 用控制流约束系统的过程管理

换句话说：

**skill 决定模型应该如何理解任务，控制流决定系统应该如何管理任务。**

这才是自然的边界。

## 6. 一个直接判据

如果还不确定某条规则该放在哪一层，可以用下面这个判据。

### 6.1 该进 skill 的规则

如果删除这条规则，模型会更容易：

- 误解任务
- 看错目标
- 漏掉关键结构
- 犯典型语义错误

那么它应该进入 skill。

### 6.2 该进控制流的规则

如果删除这条规则，模型未必立刻误解任务，但系统会更难：

- 审计
- 回放
- 交接
- 复现
- 约束多阶段写入

那么它更应进入控制流层。

这个判据的关键不在“重要不重要”，而在：

**它是在保护任务理解，还是在保护过程治理。**

## 7. 回到 `SKILL-hard.md`

围绕 `SKILL-hard.md` 的争论，真正有价值的地方就在这里。

它的问题不是“写错了控制流”。  
恰恰相反，它作为控制流，经常写得太完整了。

它的问题在于：

**把本该服务于过程治理的结构，提升成了运行时 skill 的正文。**

于是发生三件事：

1. skill 的语义目标被治理目标淹没  
2. 模型的语义压缩空间被显式状态挤占  
3. 本该由外部系统验证的结构，被迫退化成 prompt 内部的仪式化文本

这三件事叠在一起，就形成了它失败的本质。

## 8. 结论

skill 与控制流之所以应该明显分离，不是因为一个简单、一个复杂，也不是因为一个短、一个长。

真正的原因是：

**它们属于不同的计算层，服务于不同的优化目标，要求不同的表示粒度，并依赖不同的验证方式。**

因此：

- skill 应当保持为高层语义接口
- 控制流应当保持为低层治理结构

两者当然可以描述同一个任务，  
但不应该在同一层上争夺主导权。

一旦混写，LLM 就会被迫在“理解任务”和“维护过程”之间来回撕裂。  
而一旦分层，skill 才能保持它应有的作用：

不是模拟流程机，  
而是正确地塑造模型的判断方向。
