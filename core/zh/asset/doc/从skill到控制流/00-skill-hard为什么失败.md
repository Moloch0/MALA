# skill-hard为什么失败

## 1. 背景

这里保存两样东西：

- 原始的 `SKILL-hard.md`
- 围绕它展开的一次讨论记录

讨论的起点很明确：`SKILL-hard.md` 定义了大量状态、元数据、诊断、动作、版本与交接规则，结构上已经不再像一个直接服务于 LLM 的 skill，而更像一个问题构造器的控制流规约。

## 2. 最初的批评

最初的判断相当尖锐：

- `SKILL-hard.md` 把 skill 的主目标淹没了。
- 它的主要篇幅不再服务于“把坏问题修成好问题”，而是在服务于状态维护。
- 它从一个问题构造 skill，膨胀成了一个带有状态机气味的控制系统。

与之相比，`SKILL.md` 的目标非常单纯：

- 在给定目标下，用最少但充分的结构，把真正的未知暴露为可回答的问题。
- 其核心标准是 `Judgeable / Actionable / Updatable / Least but sufficient`。

因此，最初的批评是：`SKILL-hard.md` 不是更严格，而是更偏离。

## 3. 重写 hard 版的尝试，以及失败

之后曾尝试重写一个更短的 hard 版，保留以下内容：

- 区分明示、推断与未知
- 冲突不能偷偷抹平
- 证据不足时允许诚实停机

但这个方案随后被否定。原因不是它写得不够短，而是它仍然默认接受了“hard 版应该存在”这一前提。

进一步分析后，结论变成：

- 如果 hard 版没有新的独占任务，它就不该是一个独立 skill。
- 如果它的附加要求都可以被 `SKILL.md` 吸收，它就没有必要以第二份文件存在。
- 一个没有独立边界的“严格版”，本质上只是重复版。

因此，一度得出的结论是：`SKILL-hard.md` 不该重写，而应被删除，或至多被基础版吸收。

## 4. 讨论的转折

随后出现了一个更细的判断：

`SKILL-hard.md` 本身并不是一个糟糕的控制流设计。恰恰相反，它在控制流意义上相当完备，甚至可以说做得不错。

真正的问题在于，它和自然语言推动的 LLM 之间存在巨大张力。

这个张力可以表述为：

- 问题分解在逻辑上确实可以写成一连串 `if / else`
- 但 LLM 的优势，恰恰在于能够把许多细粒度判断压缩成更高层的语义判断
- 如果把所有细节判断都显式写出来，模型就会把大量认知资源耗在流程维护上，而不是耗在理解问题本身上

于是就会出现一种典型失败：

- 模型不再优先修复问题
- 模型开始优先维护诊断、动作、路由、版本与终点
- 结果不是更可靠，而是陷入逻辑迷宫

## 5. 当前形成的看法

目前形成的看法不是简单的“hard 错，simple 对”，而是更分层的判断。

### 5.1 `SKILL-hard.md` 的价值

它有价值，但价值不在“直接给 LLM 当运行时 skill”。

它更适合作为：

- 设计者的后台规约
- 对问题构造流程的控制流分析
- 调试失效案例时的故障树
- 离线评估或审查时的参考框架

### 5.2 `SKILL.md` 的价值

它更适合作为：

- 给 LLM 直接执行的 skill
- 运行时使用的正文
- 保持高层约束、低层压缩的最简形式

它不把控制流全部展开，而是保留最少但充分的结构，让模型自己完成大量局部判断。

### 5.3 核心区分

这次讨论最终得到的核心区分是：

**写给 LLM 的规范，不应该等于写给编排器的规范。**

或者换一种说法：

- 显式控制流追求可检查性
- 自然语言驱动的 LLM 追求语义压缩

两者都不是错的，但它们适合放在不同层。

## 6. 暂时的结论

因此，当前最稳妥的理解不是：

- `SKILL-hard.md` 完全无价值

而是：

- `SKILL-hard.md` 作为控制流文档是有价值的
- `SKILL-hard.md` 作为直接运行的 skill 正文则和 LLM 存在明显张力
- `SKILL.md` 更适合作为运行时版本
- `SKILL-hard.md` 更适合作为分析、设计、评估或归档材料

## 7. 这份归档的意义

把这份讨论和 `SKILL-hard.md` 放在同一个目录下，不是为了给 hard 版正名，也不是为了立即废弃它，而是为了保留一个清楚的中间判断：

- 它并非“错误文档”
- 它是“放错层的文档”

从 skill 走到控制流，本身就是一次抽象层级变化。  
这个目录名“从 skill 到控制流”，记录的正是这件事。
